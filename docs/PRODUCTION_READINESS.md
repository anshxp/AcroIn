# AcroIn Production Readiness

This document defines the minimum operational bar for AcroIn production deployments.

## Service topology

- Web frontend talks to the Node backend over HTTPS.
- Mobile talks to the Node backend over HTTPS.
- Node backend is the public API boundary.
- Recommendation and face services are private/internal services and require service-to-service API keys in production.
- MongoDB is reachable only by server-side services.

## Required production configuration

Backend:

- `NODE_ENV=production`
- `MONGO_URI`
- `JWT_SECRET` (at least 32 random characters)
- `FRONTEND_URL` / `FRONTEND_URLS`
- `RECOMMENDATION_SERVICE_URL`
- `RECOMMENDATION_API_KEY`
- `FACE_REC_SERVICE_URL`
- `FACE_API_KEY`

Recommendation service:

- `ENVIRONMENT=production`
- `RECOMMENDATION_API_KEY`
- `MONGO_URI`
- `ALLOWED_ORIGINS`

Face service:

- `ENVIRONMENT=production`
- `FACE_API_KEY`

Never commit real values to Git. Use the deployment provider's secret store.

## Deployment order

1. Create production MongoDB database and indexes.
2. Deploy recommendation service.
3. Deploy face-auth service.
4. Deploy Node backend with both internal service URLs and API keys.
5. Deploy frontend with only the public backend URL.
6. Configure mobile production API URL.
7. Run smoke tests against staging.
8. Promote to production only after CI and smoke tests pass.

## Smoke tests

- `GET /health` returns 200 with database connected.
- `GET /ready` returns 200 only when the backend is ready.
- Face service `/` returns 200.
- Recommendation service `/recommendations/health` returns 200.
- Unauthenticated protected API calls return 401.
- Unauthorized roles return 403.
- Invalid face uploads return 4xx, never a false 200.
- Recommendation requests from browsers are rejected at the service boundary unless they carry the internal API key.
- Frontend recommendations are generated by the backend recommendation route, not client-side scoring.

## Security requirements

- HTTPS only in production.
- No wildcard CORS.
- JWT secret is never logged or returned.
- Authentication endpoints are rate limited.
- General API requests are rate limited.
- Request IDs are returned for support/debugging.
- Error responses do not expose stack traces or internal exceptions.
- Upload endpoints enforce file type and size validation.
- Biometric data is access-controlled and must have an explicit retention/deletion policy.

## Data protection

Use separate staging and production databases. Configure automated MongoDB backups and periodically test restoration. Do not use real production biometric or student data in CI.

## Release gate

A release is production eligible only when:

- frontend lint/build passes;
- backend syntax/tests pass;
- Python tests pass;
- mobile type checking passes;
- security/dependency checks pass;
- staging smoke tests pass;
- rollback procedure is known and tested;
- required production secrets are configured outside Git.
